# Chrono Timer --- Android App & Feature Expansion Proposal

**Document type:** Product vision, feature proposal and technical
planning document\
**Project:** Chrono Timer\
**Status:** Proposal for discussion --- not an implementation approval\
**Prepared:** 14 November 2026

------------------------------------------------------------------------

## 1. Project Vision

The goal is to evolve the existing Chrono Timer web project into a
polished Android application that behaves like a normal installed
Android app while preserving the current timer experience.

The app should:

-   Install on compatible Android phones using an APK.
-   Open from its own launcher icon, without requiring the user to open
    a browser.
-   Keep the existing timer design, themes and calculation behaviour
    intact.
-   Work offline for core timer functions.
-   Optionally use Android capabilities such as location, notifications,
    vibration and device sensors.
-   Add useful utility features such as weather, world clock, battery
    information and home-screen widgets.
-   Keep permissions optional, understandable and limited to features
    that need them.

The first release should remain focused: **Chrono Timer is primarily a
clock and timer app**, with additional utilities available without
making the main timer screen cluttered.

## 2. Recommended Technology Direction

### Recommended approach: Capacitor + Android native capabilities

The existing project is based on web technologies (HTML, CSS and
JavaScript). Capacitor can package that application inside an Android
project and provide access to native Android functionality through
plugins or custom native code.

This avoids rebuilding the entire user interface from scratch.

Suggested structure:

``` text
chrono-timer/
├── web/                       # Existing HTML, CSS, JavaScript and assets
│   ├── index.html
│   ├── app.js
│   ├── style.css
│   ├── assets/
│   └── ...
├── android/                   # Android Studio project generated by Capacitor
├── capacitor.config.*
├── package.json
└── docs/
    └── CHRONO_ANDROID_APP_PLAN.md
```

The actual folder names should be adjusted to match the existing
repository. Do not move or overwrite files until the current project has
been inspected.

### Why Capacitor is recommended

-   Reuses the existing timer interface and much of its code.
-   Produces an Android project that can be opened in Android Studio.
-   Supports native plugins for notifications, haptics, device
    information and other capabilities.
-   Allows a later PWA release to coexist with the Android app.
-   Makes it possible to add custom native Android code for features
    that standard plugins do not cover.

### Alternative: PWA packaged as an Android app

A hosted PWA can be packaged using a Trusted Web Activity approach. This
is useful when the website itself is the primary product. However, it
depends more heavily on a properly hosted website and domain
verification. It is not the first choice if the goal is a self-contained
offline-first APK with deeper native integration.

## 3. App Packaging and Distribution

### Android APK

An APK is an Android installation package that can be shared directly
with users. A user can install it on a compatible Android device,
subject to Android's installation and security prompts.

### Android App Bundle (AAB)

An AAB is generally used when publishing through Google Play. It is not
normally the file shared directly for manual installation.

### Suggested delivery outputs

-   Debug APK for development testing.
-   Signed release APK for direct distribution.
-   AAB if the app is later published on Google Play.
-   Source project and build instructions, so future versions can be
    rebuilt.

### Important compatibility note

One APK can support many Android phones, but it cannot be guaranteed to
work identically on every device. Android version, screen size,
manufacturer power-management behaviour, sensors and permissions can
differ. Test on a range of devices before public distribution.

## 4. Main App Navigation and Layout Proposal

The timer must remain the primary feature. Additional utilities should
not dominate the main timer screen.

### Proposed navigation

    -   Main stopwatch or countdown interface.
    -   Compact weather card (optional).
    -   Quick access to common timer presets.
2.  **Weather**
    -   Current conditions and forecast.
    -   Location and refresh controls.
3.  **Clock**
    -   Digital clock, date and world clocks.
4.  **Tools**

This is a proposed information architecture, not a locked design. The
final navigation should be discussed before implementation.

## 5. Weather Feature

### Purpose

Show useful local weather information inside Chrono Timer.

### How it works

The phone can provide its location if the user grants permission. The
app then requests weather information from an online weather provider.
The phone's location sensor does **not** directly measure the weather.

### Proposed information

-   Current temperature.
-   Weather condition, such as clear, cloudy or rainy.
-   Feels-like temperature, if provided.
-   Humidity.
-   Wind speed and direction, if available.
-   Sunrise and sunset.
-   Today's high and low.
-   Hourly forecast.
-   Multi-day forecast.

### User experience

Recommended behaviour:

-   Show a small weather card on the Home / Timer screen.
-   Tapping the card opens a full Weather page.
-   Provide a refresh action and show the last updated time.
-   Allow manual city selection if location permission is denied.
-   Allow the user to disable weather completely.
-   Use a clear offline or unavailable state when data cannot be
    fetched.

### Permissions and privacy

-   Request location only when the user enables location-based weather.
-   Prefer approximate location unless precise location is genuinely
    needed.
-   Explain why location is requested before the system permission
    prompt.
-   Do not collect or store location history.
-   Provide a manual city option.
-   Weather updates require internet access; cached last-known
    information may be displayed with its timestamp when offline.

### Weather provider considerations

A weather service/API will be required. Before choosing one, compare:

-   Free-tier limits and pricing.
-   Attribution and display requirements.
-   Forecast coverage for the intended regions.
-   API key security and restrictions.
-   Data refresh limits and caching rules.
-   Commercial-use terms.

Do not place a private API secret directly in publicly distributed
client-side JavaScript. If the provider requires a protected secret, use
an appropriate backend/proxy or a provider-supported restricted key
arrangement.

## 6. Clock and World Clock

### Proposed features

-   Large digital clock.
-   Current date and day.
-   Optional seconds display.
-   12-hour / 24-hour format.
-   World clock for user-selected cities.
-   Multiple time zones.
-   Optional date display for each city.

The clock should use the device's system time and time-zone database.
The app should respond correctly when the device time zone changes.

## 7. Alarm, Countdown and Notifications

### Proposed features

-   Countdown completion notification.
-   Optional sound and vibration.
-   User-selectable alert sound.
-   Multiple saved countdown presets.
-   Optional alarm screen when a timer completes.
-   Clear controls to stop or dismiss an alert.

### Android behaviour and limitations

Android places restrictions on background work and exact alarms. A
normal background JavaScript timer is not a reliable way to guarantee an
alert at an exact future time.

For dependable scheduled alerts, evaluate Android's native
alarm/notification APIs and current Android permission requirements.
Exact alarm access may require special handling and should only be
requested if the feature genuinely needs it.

The app must clearly communicate what works when: - The app is
visible. - The app is in the background. - The app has been removed from
recent apps. - The phone restarts. - Battery Saver or
manufacturer-specific battery restrictions are active.

Do not promise that every timer or alarm will always fire under every
device condition until tested.

## 8. Battery Information

### Proposed information

-   Battery percentage.
-   Charging / discharging state.
-   Plugged-in status, where available.
-   Battery health or temperature only if the device and Android API
    expose reliable values.

### Limitations

Not every Android device exposes every battery detail. Battery health
and temperature should be shown only when available and should not be
presented as medical-grade or service-diagnostic measurements.

Keep this feature informational. Avoid unnecessary continuous polling
because it can consume battery.

## 9. Compass and Device Sensors

### Proposed compass feature

-   Show compass direction.
-   Show heading in degrees.
-   Optional calibration guidance.
-   Explain when the device lacks a suitable sensor.

### Considerations

-   Some phones do not have all required sensors.
-   Magnetic interference can make readings inaccurate.
-   Sensor readings should be treated as approximate.
-   Ask for no unrelated permissions.
-   Provide a clear unsupported-device state rather than displaying
    fabricated values.

## 10. Timer History, Laps and Presets

### History

-   Recent stopwatch sessions.
-   Lap records.
-   Countdown sessions.
-   Completion time and duration.
-   Optional user-defined labels.
-   Clear history action with confirmation.

### Presets

-   Save frequently used countdown durations.
-   Give presets short names.
-   Edit and delete presets.
-   Provide quick-start controls.
-   Store presets locally on the device by default.

### Data handling

Use local storage/database suitable for the app. If backup or cloud sync
is ever added, make it optional and explain what data is uploaded.

## 11. Android Home-Screen Widgets

Possible widgets:

-   Digital clock widget.
-   Compact weather widget.
-   Quick countdown preset widget.
-   Active countdown status widget.

Widgets are a separate Android implementation task; they are not
automatically created just because the app uses Capacitor. They may
require native Android code and Android App Widget APIs.

Widget updates are controlled by Android and are not guaranteed to
refresh every second. Therefore, a widget should not be treated as a
precision live stopwatch display. It can show useful summaries and
refresh within platform limits.

## 14. Timer Accuracy and Background Behaviour --- Critical Requirement

This is one of the most important engineering areas.

A timer must not rely only on repeatedly decrementing a JavaScript
counter with `setInterval()`. Android may throttle or suspend app
execution when the app is in the background.

Recommended timing model:

-   Store a start timestamp for a running stopwatch.
-   Store an end timestamp for a countdown.
-   Recalculate displayed time from the current clock whenever the app
    resumes or refreshes.
-   Use native Android scheduling/notifications for alerts that must
    occur while the app is not active.
-   Handle device restart and time changes deliberately.
-   Test behaviour with screen off, battery saver, app backgrounded and
    app process removed.

A Service Worker is not a permanent background timer and cannot
guarantee that a timer continues executing while the app is closed.

## 17. Development Roadmap

### Phase 0 --- Audit and protect the current project

-   Inspect the latest source ZIP/repository.
-   Identify the actual entry point, assets and build process.
-   Verify all current timer modes and calculations.
-   Confirm the plain-number design requirement.
-   Record existing bugs and known platform limitations.
-   Create a clean backup or version-control checkpoint.

**Completion condition:** Existing project can be built and tested
before Android conversion.

### Phase 1 --- Android app foundation

-   Add Capacitor to the project.
-   Create Android project.
-   Set app name, package ID, version and icon.
-   Configure splash screen and status/navigation bars.
-   Build a debug APK.
-   Test installation and basic operation on Android.

**Completion condition:** The timer installs and opens as a normal
Android app.

### Phase 2 --- Core timer reliability

-   Preserve stopwatch, countdown, interval and live clock.
-   Verify timer calculations.
-   Add timestamp-based timing recovery.
-   Test screen off, app background, app resume and process recreation.
-   Decide and implement native alert behaviour.

**Completion condition:** Core timer behaviour is verified under defined
Android conditions.

### Phase 3 --- Native user experience

-   Notifications.
-   Sound and vibration.
-   Screen keep-awake option.
-   Permission explanations and settings.
-   Test denial and revocation of permissions.

**Completion condition:** Native features work without breaking basic
timer operation.

### Phase 4 --- Weather

-   Choose weather provider.
-   Implement optional location permission.
-   Add manual city selection.
-   Add compact Home weather card and detailed Weather page.
-   Add caching, refresh and offline states.
-   Review API key security and provider terms.

**Completion condition:** Weather works with permission, without
permission and offline.

### Phase 5 --- Additional utilities

-   World clock.
-   Battery information.
-   Compass.
-   Timer history and presets.

Implement and test each as an independent module.

### Phase 6 --- Home-screen widgets

-   Decide which widgets are genuinely useful.
-   Implement native Android widgets.
-   Test refresh behaviour and battery impact.

### Phase 7 --- Release preparation

-   Test multiple screen sizes and Android versions.
-   Test installation, upgrade and uninstall/reinstall behaviour.
-   Check app permissions and privacy disclosures.
-   Generate signed release APK.
-   Generate AAB if Google Play distribution is planned.
-   Document versioning and update process.

## 19. Privacy and Security Principles

-   Do not request permissions that the app does not need.
-   Do not collect or upload location history.
-   Keep timer history and presets on-device by default.
-   Explain why each permission is requested.
-   Provide controls to disable optional modules.
-   Protect API credentials; do not ship private secrets in client code.
-   Do not silently transmit personal data.
-   Publish a privacy policy before public distribution if required by
    the distribution channel or applicable rules.

## 21. Recommended First Release

To keep the first release useful and achievable, the recommended scope
is:

**Include** - Existing Chrono Timer features. - Android APK packaging. -
Offline core timer. - Reliable timestamp-based timer calculations. -
Native notifications, sound and vibration, subject to Android
restrictions. - Optional weather with compact Home card and detailed
page. - Manual city selection. - Local timer history and presets. -
Existing themes and settings.

**Consider for a later release** - World clock. - Battery information. -
Compass. - Home-screen widgets. - Quick Settings tile. - Additional
focus and productivity tools.

This staged approach reduces risk and makes it easier to test each
feature without damaging the existing timer.

## Final Project Rule

**Do not change existing timer calculations, timer modes, themes or
layout as an unrelated side effect of Android integration.** First audit
and preserve the current project, then implement each approved feature
as a separate module. This document is a proposal and planning
reference; no implementation is authorized merely by creating this
document.
